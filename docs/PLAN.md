# 鲸坞 · 技术规划

> 2026-11-13 写。基于当天 v2.5.0 的代码状态。
> 这份文档回答一个问题：**接下来钱和精力该花在哪**。
> 结论在第一节，证据在第二节，方向评估在第三节。

---

## 一、结论

按「投入产出比 × 紧迫程度」排序，我的判断是：

| 优先级 | 方向 | 理由（一句话） |
|---|---|---|
| **P0** | 测试体系改造 | 87 处断言是"源码里有没有这段字符串"，过去三天因此返工 3 次 |
| **P1** | 远程 DSH 收尾 | 功能已完整，但最关键的复用判据没在真机验证过，不能一直挂"实验" |
| **P1** | 分发包瘦身与首启体验 | 102 MB / 首启 15 秒，是用户最先感知到的两件事 |
| **P2** | 平台抽象层 | 为跨平台铺路，成本可控，但**不等于**跨平台 |
| **P3** | 跨平台（macOS / Linux） | 成本被严重低估：不是"Qt 跨平台所以改改就行" |
| **不做** | 自动降级、后台常驻预热、多窗口 | 已被明确否决过，记录在案避免反复 |

**对你提的跨平台，我的结论是：方向对，但现在做会亏。**

理由不是"做不到"，而是**它的成本结构和这个项目的现状不匹配**——跨平台要重写
约 4000 行平台相关代码、维护三套打包链路、还要面对 macOS 的签名公证
（这不是代码问题，是每年 99 美元的账号加一条发布流水线）。而当前唯一的用户
就在 Windows 上，且我们连 Windows 自己的测试都不牢。

更划算的顺序是：**先把 P0 做完，让"改一处不炸三处"成立；再谈平台扩张。**

## 三、短板诊断

### 3.1 测试体系：87 处断言在检查"源码里有没有这句话"

`tools/gui_selftest.py` 1,913 行里：

- **87 处**是"从源码里找字符串"（`"def _abort" in gui`、`"程序不会自己" in panel`）
- **5 处**用 `inspect.getsource` 取函数源码比对
- 只有 **26 处**是真正的运行时断言（构造对象、检查属性、验证行为）

这种做法有它的道理——它能在不启动 GUI、不装 DSH 的前提下守住"某段修复没被改回去"。
但代价在过去三天集中爆发了：

**证据一**：改产品名（桌面壳 → 鲸坞）时，一条断言写死了 `"桌面壳" in t`，直接变红。
而它守的语义是"两种更新别混在一起"，和名字无关。

**证据二**：打磨文案时，`"程序不会自己" in panel` 变红。它守的是"不再承诺自动降级"。

**证据三**：拆分文件后，`gui` / `panel` / `dev` 三个变量读的还是旧路径，
**整套断言静默失效**——不报错、不失败，只是再也不检查了。这比变红危险得多。

**证据四**：`local_checks` 整个函数在拆分中丢失，静态自测全绿。
真机上表现为"状态检测页永远停在检测中"。

结论：现在的测试**能守住"代码长得像上次"，守不住"行为是对的"**。
而重构（恰恰是最需要测试保护的时候）会让它大面积失效。

### 3.2 远程功能停在"能连但没验过"

代码完整（954 行），本地用假服务验证过脚本契约，但**最关键的判据没验**：
"复用远端上次启动的实例"。这条只在真机上才有意义，而 frp 隧道因欠费下线，
一直没等到验证窗口。所以它现在挂着"实验"标签。

一个功能挂"实验"太久，会变成没人敢动的灰色地带。

### 3.3 README 的「已知限制」已经不准了

上面写着"应用被强制结束时服务一并终止（不脱离 Job Object）"——
**v2.5.0 已经修掉了**，现在崩溃/强杀由系统收尸。文档比代码落后一版。

（这条本身就是 3.1 的佐证：没有测试能检查"文档和实现是否一致"。）

## 四、方向评估

### P0 · 测试体系改造

**目标**：让"行为测试"成为主力，源码字符串断言退到只守少数几条无法运行时观测的契约。

做法：

1. **给界面层补"可测性入口"**：现在大部分逻辑藏在 Qt 槽函数里，只能靠读源码确认。
   把纯逻辑抽成不带 Qt 的函数（就像 `nav_disposition`、`plan_service` 那样），
   直接单元测试。这类函数已经有几个，可以继续扩大。
2. **用无头窗口跑行为断言**：`QApplication` + 离屏渲染已经能做（`shoot_panel.py` 就是这么截图的），
   可以断言"切到状态检测页 → 200ms 内出现 6 项结果"，而不是"源码里有 `local_checks`"。
3. **给"断言绑死文案"设一道闸**：凡是比对中文字符串的断言，必须说明它守的语义是什么，
   并优先改成语义判据（例如"不含『自动降级』且含『不会自行』"）。
4. **拆分后固定动作**：用 AST 对比"拆分前顶层定义"与"拆分后各模块定义"的差集，必须为空。
   这次就是靠它捞回 `local_checks` 和 `LEVEL_NAMES` 的。

成本：约 2~3 个工作日。收益：后续每次改动都更敢下手。

### P1 · 远程 DSH 收尾

等隧道恢复后跑三件事：首次连接打印"本次启动"并留四个状态文件 → 断开再连打印
"复用已运行的实例" → 只碰 `~/.dsh-remote`、结束时停掉远端进程。

验证通过就去掉"实验"标签。若判据有问题，按真机日志修。

成本：半天（含等待）。**阻塞项：frp 隧道恢复。**

### P1 · 分发包瘦身与首启体验

两个数字最刺眼：**102 MB** 和 **首启 15 秒**。

- 体积：大头是 PySide6 + QtWebEngine。可查 `packaging-trim.md` 里已有的裁剪记录。
  进一步的空间在"剔掉用不到的 Qt 模块与语言包"——CI 里已经在剔语言包，可以继续。
  但要说清楚：**这不是线性收益**，压到 80 MB 需要动 Nuitka 的排除策略，有风险。
- 首启：10.8 秒是 DSH 自己的模块加载，壳侧插不进去。能做的只有**感知优化**
  （加载页的真实进度、首屏骨架），以及**降低二次启动的等待**（现在已能接管服务，
  但界面仍然要等 WebEngine 起来）。

成本：1~2 天。收益：口碑。

### P2 · 平台抽象层

把"跟操作系统打交道"的部分抽成接口：

```
dsh_host/platform/
  __init__.py      探测并选择实现
  base.py          接口定义（窗口装饰 / 进程管理 / 自更新 / 环境供给 / 内存采样）
  windows.py       现有实现搬进来
  (macos.py)       将来
```

**这不是跨平台，只是把跨平台的成本变得可分期**。做完之后：

- Windows 实现更清晰（现在 `contract.py` 里混着 DETACHED、taskkill、路径判断）
- 将来加平台是"新增一个文件"，不是"改六个文件"
- 风险可控：行为不变，可以用现有自测兜底

成本：2~3 天。**收益是"选择权"，不是功能。**

### P3 · 跨平台：为什么现在做会亏

#### 成本拆解

| 模块 | 行数 | 迁移难度 |
|---|---|---|
| `dwm.py` 标题栏取色 | 798 | **重写**。macOS 要 NSWindow/NSVisualEffectView，Linux 要 X11/GTK，没有可移植的同构 API |
| `selfupdate.py` 自更新 | 1,323 | **重写**。exe 就地替换 + 批处理 → macOS 要处理 .app bundle、签名失效、公证；Linux 要 AppImage/包管理器 |
| `jobobj.py` 进程回收 | 218 | **重写**。macOS 用进程组 + `PR_SET_PDEATHSIG`（Linux），语义还不完全等价 |
| `provision.py` 环境供给 | 309 | **重写**。winget → brew / apt，还要处理"用户没装 Homebrew" |
| `contract.py` 进程管理 | 1,025 | **适配**。`DETACHED_PROCESS` → `start_new_session`，`taskkill` → `killpg` |
| `procmem.py` 内存采样 | 189 | **适配**。`tasklist`/WMI → `ps` / `/proc` |
| `config.py` 路径 | 约 300 | **适配**。`%LOCALAPPDATA%` → `~/Library/Application Support` / `~/.local/share` |
| `dsh_ui/` 界面层 | 6,800 | **不用改，但要全量验证**。QtWebEngine 在各平台渲染差异、字体、DPR、菜单样式 |

**合计约 4,200 行平台相关代码要重写或适配**，界面层 6,800 行要逐页目视核对。

#### 被低估的三件事

1. **macOS 分发不是技术问题，是账号问题。** 未签名未公证的应用，用户双击会被
   Gatekeeper 拦下并提示"已损坏"。要消除它必须：Apple Developer 账号（99 美元/年）
   + 公证流程（`notarytool`）+ CI 里保管证书。这跟写代码完全是两回事。
2. **自更新在 macOS 上本质不同。** Windows 允许替换正在运行的 exe（rename 后写新的）；
   macOS 的 .app 是目录，替换时签名会失效，通常要重新走公证校验。现有的
   "下载 → 替换 → 重启"套路不能直接搬。
3. **三套打包链路 = 三倍的维护面。** 现在 CI 只有一条 Windows 流水线，9 分钟。
   加 macOS 要 GitHub 的 macOS runner（费用更高），Linux 要处理 WebEngine 的动态库依赖。

#### 什么时候该做

满足**任一条**再启动：

- 有明确的、非假设的用户需求（比如合作教师里有人用 Mac，且愿意当测试者）
- 项目要脱离"自用工具"定位，面向陌生人分发
- P0 已完成——否则跨平台会同时放大"改动容易炸"的问题

#### 如果一定要做，正确顺序

1. 先做 P2 的平台抽象层（2~3 天，行为不变）
2. 只做 **macOS**，不做 Linux（Linux 桌面用户里愿意用商业桌面壳的比例低，
   而打包与 WebEngine 依赖的坑最多）
3. macOS 第一版**明确不做自更新**（让用户手动下载替换），把公证流程单独啃

### 不做清单（已有结论，避免反复讨论）

| 方向 | 否决理由 | 时间 |
|---|---|---|
| 崩溃后自动降级为软件渲染 | 是概率缓解不是修复，且与"用户选了硬件加速"冲突 | 2026-10-25 |
| 退出后保留后台 node / 开机自启预热 | 用户原话「不能到处留垃圾」 | — |
| 后台 discard 视图 | 会打断正在流式输出的回复 | 2026-11-12 |
| 自行编译或 patch QtWebEngine | 维护成本远超收益，上游已修 | 2026-10 |

## 五、建议路线

```
现在 ──► P0 测试体系（2~3 天）
          │  产出：行为断言替代字符串断言；拆分检查固化成工具
          ▼
        P1 远程收尾（等隧道，半天）+ 瘦身/首启（1~2 天）
          │  产出：去掉"实验"标签；包体和首屏各改善一档
          ▼
        P2 平台抽象层（2~3 天）
          │  产出：新增平台 = 新增一个文件
          ▼
        ── 到这里再决定要不要跨平台 ──
```

**关键判断点在第 2 步之后**：如果那时跨平台的需求依然只是"也许将来有人用 Mac"，
就不做。抽象层已经买下了选择权，不必提前付全款。
