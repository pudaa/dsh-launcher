# v2.4.3 — 不再把自己降级，并把上游修复拿到手

这一版做两件事，它们其实是同一件事的两头：

1. **撤掉"崩溃后自动降级软件渲染"** —— 它会让窗口莫名其妙变慢，而且自己出不来。
2. **把 PySide6 升到 6.11.3** —— 这是第一个真正含 QTBUG-142165 修复的可安装版本。

## 症状：窗口"突然就不跟手了"

现象是鼠标划过按钮、链接、列表行时，hover 状态要慢半拍才出现；滚动发黏，
输入有延迟。但同机其它 Electron 应用完全正常，所以很容易怀疑到"是不是装了什么
插件"或者"是不是 DSH 前端变重了"。

真相在日志第一屏：

```
WebEngine flags: --lang=zh-CN --disable-gpu
（硬件加速=关；上次运行未正常退出（疑似 GPU 崩溃），本次自动降级为软件渲染）
```

而 `settings.json` 里 `webengine_hw_accel` 明明是 `true`。**是壳自己把它否决了。**

现场三条硬证据（2026-10-29 实测）：

| 项 | 观测 |
|---|---|
| 启动 flags | `--disable-gpu` |
| 渲染子进程 | 只有 `renderer` + `utility`，**没有 `gpu-process`**（对照：同机其它应用有 11 个 GPU 进程） |
| renderer CPU | 存活 5 分钟累计 **295.8 s ≈ 98% 单核** |

## 根因一：崩溃哨兵会自我锁死

v2.4.1 引入过一套"崩溃哨兵"：

```python
# 启动即写哨兵，正常退出才删
_write_webengine_marker(...)
atexit.register(_clear_webengine_marker)
```

下次启动如果还能读到它、且 `started_at` 在 **12 小时**内，就判定"上次没正常退出"
（疑似 GPU 崩溃），本次自动加 `--disable-gpu`。

问题在于它是个**正反馈**：

```
降级 → 更卡 → 用户更容易直接关窗口 / 任务管理器结束 → 又被记成"未正常退出" → 继续降级
```

日志能直接看到这条链——**2026-10-24、10-25、10-26、10-27、10-29 17:54 每一次启动
都在降级**，机器已经在这个状态里待了五天，用户只感觉到"说不清为什么变慢"。

顺带一个教训：`taskkill /F` 这种强杀不给解释器跑 `atexit` 的机会，等于亲手喂它一次
"未正常退出"。**停这个程序请走托盘或面板的退出。**

## 根因二：崩溃本身现在能修了

QTBUG-142165 的根因（ANGLE D3D11 的 `PackedAttributeLayout` 带着未初始化的填充字节
参与 `InputLayoutCache` 哈希，导致缓存渐进损坏后读到已析构对象）已由上游定位，
三个 backport 于 **2026-10-08 17:56 UTC** 合入 140-based 分支。

但"修了"和"能装到"是两个问题。判据不能看版本号，要看 DLL 的 PE 构建时间和
崩溃点那 96 字节机器码——`tools/webengine_fix_check.py` 就是干这个的：

| 构建 | Chromium | DLL PE 构建时间 | 崩溃指纹 | 含修复？ |
|---|---|---|---|---|
| PySide6 6.11.2（旧） | 140.0.7339.225 | 2026-08-13 01:59 UTC | 找到（0xd21aa3） | ❌ |
| PySide6 6.12.0 → WebEngine 6.12.0.140 | 140.0.7339.225 | 2026-09-27 12:38 UTC | 找到 | ❌ 逐字节相同 |
| 修复 backport 合入 | — | **2026-10-08 17:56 UTC** | — | （分水岭） |
| **PySide6 6.11.3（本版）** | **140.0.7339.264** | **2026-10-21 01:32 UTC** | **未找到** | ✅ |

`6.11.3` 于 2026-10-26 才上 PyPI（11 天前查还是"6.11 线收尾在 6.11.2"）。
两条判据同时满足：PE 构建晚于修复合入时刻，**且**崩溃点机器码完全消失——
不是"版本号更新"蹭出来的假信号。

选 6.11 线而不等 6.12：6.12 把 WebEngine 拆成独立 wheel
（`PySide6_WebEngine==6.12.0.140`），升上去打包链路要跟着改双 wheel，而它至今不含
修复（`6.12.0.1` 到 10-29 仍未发布）。6.11.3 是补丁版，DLL 之外没有结构性变化。

## 结果

| 项 | v2.4.2 | v2.4.3 |
|---|---|---|
| 硬件加速来源 | 用户设置 **被** 哨兵否决 | 用户设置是**唯一**来源 |
| 崩溃后行为 | 自动降级一次（且会反复） | 什么都不做，如实崩溃 |
| WebEngine | 6.11.2（含缺陷） | 6.11.3（含官方修复） |

`purge_legacy_webengine_state()` 会在启动时清掉旧版留下的
`webengine-state.json`——一个再没人读的状态文件留在数据目录里，下次排查时会被
当成有效信息误导人。

自测加了反向钉子，把"不许偷偷改配置"钉死：

- 源码里不允许再出现 `CRASH_FALLBACK_WINDOW_S` / `_write_webengine_marker` /
  `_read_webengine_marker` / `_clear_webengine_marker`
- 不允许再出现"兼容模式"这类静默降级提示
- `_hw_accel_enabled()` 必须是唯一的加速判定入口

## 一个诚实的说明

撤掉自动降级**不是**因为崩溃修好了才敢撤——两件事是分别判断的：
自动降级的代价（全体用户、全部时间的性能）远大于它兜住的那点概率，
这个取舍 2026-10-25 就该做，只是拖到今天才发。

所以万一 6.11.3 之后仍有残留崩溃，**本版的行为是如实崩溃，而不是偷偷变慢**。
真遇到就提供 `%LOCALAPPDATA%\CrashDumps\` 的转储，别用降级去掩盖。

## 顺带

- 升到 6.11.3 的完整取证、被否掉的四条路（自动降级 / 自动拉起 / 换 ANGLE 后端 /
  自己打补丁）都记在 `docs/webengine-angle-crash.md`，下次不要重走。
- `tools/webengine_fix_check.py` 已支持直接吃 wheel 判定，未来 PySide 再发新版，
  先跑它再决定要不要动 `requirements.txt`。
- `tools/zen_pool_probe.py` 加入工具集：查免费模型通道的出口 IP 配额状态。
