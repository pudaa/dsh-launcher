# v2.5.1 — 修复 v2.5.0 更新失败

这是一个**紧急修复**：v2.5.0 的 exe 下载完成后通不过候选版本自检，更新会中止
（"新版本已下载，但无法启动"）。已装上的 v2.5.0 仍可使用，只是没法从旧版升上来。

## 症状

更新进度走满 102.6 MB 之后报：

```
候选版本自检未通过（退出码 3）：SVG 渲染上色比例 = 0.313（正常）；结论 = **失败**
```

"上色比例正常"和"结论失败"自相矛盾，看不出到底哪一步坏了。

## 两个独立的问题

### 1. 资源路径（真正的失败原因）

`_asset_dir()` 原先住在根目录的 `dsh_gui_qt.py`，它用 `dirname(__file__)` 找
`assets/`——那时正好是项目根 / onefile 解包根，所以能用。

v2.5.0 把界面层拆成 `dsh_ui/` 包时，这个函数搬到了 `dsh_ui/prelude.py`，
但**算式没跟着改**：同一个 `dirname(__file__)` 现在指向 `dsh_ui/` 子目录，
于是去找 `dsh_ui/assets`（不存在）。剩下的兜底只有 cwd。

- 从仓库根目录跑 → cwd 里有 `assets/` → 自检通过 ✓
- 从桌面快捷方式、临时目录跑 → 找不到 → **图标检查失败，自检退出码 3** ✗

修复：候选基准改成**包的上一级**（`dirname(dirname(__file__))`），源码直跑和
onefile 解包两种形态都重新指向 `assets/` 的父目录。

### 2. 错误信息把原因丢了

`preflight()` 取报告时写的是：

```python
# 自检报告最后一行是"结论 = ..."，前面都只是环境信息
detail = "；".join(lines[-2:])
```

这个假设是错的：报告里以 `↑` 开头的行才是失败原因，它们恰恰在前面。
结果用户只看到最后两行——一个"正常"的指标和一个"失败"的结论。

现在改成提取所有 `↑` 行；`resource_report()` 也把失败项汇总成独立的
`失败项 = ...` 一行。

## 为什么 CI 没拦住

CI 的"在产物上做资源自检"这一步是在**仓库根目录**跑 `./build/DSH-Web.exe`。
那里就有 `assets/`，cwd 兜底命中，坏包照样绿。

现在改成：把 exe 复制到一个空目录，从那里启动。cwd 和 exe 所在目录都没有
`assets/`，唯一还能命中的就只有**解包目录里的资源**——也就是我们真正要验的东西。

用旧的 v2.5.0 产物在新流程下复跑，退出码 3、`ASSET_DIR` 指向不存在的
`dsh_ui\assets`，确认这道检查确实能拦住这个 bug。

## 升级

- 已是 **v2.5.0**：这一版的修复只影响"新包能不能通过自检"，直接更新即可。
- 仍是 **v2.4.x**：正常更新到 v2.5.1，会跳过 v2.5.0。

更新成功后，第一次启动如看到"已接管一个正在运行的背景服务"的气泡，
那是上一版留下的服务；退出一次就干净了。
