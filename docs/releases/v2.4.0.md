# v2.4.0 — 更新下载改为多连接并行，从 40 分钟降到几分钟

这一版只做一件事：**把「下载并更新」这件事从"要等半小时"变成"几分钟"**。

## 慢在哪：不是网速问题，是单条连接被限速

先量了一下真实情况（就是这个 107 MB 的安装包，走本机网络）：

| 方式 | 速度 | 下完 107 MB 需要 |
|---|---|---|
| 单条连接（以前的实现） | **0.04 MB/s**（约 40 KB/s） | **约 43 分钟** |
| 8 条连接并行 | **0.28 ~ 0.42 MB/s** | **6 分钟** |

单连接那个速度连续 140 秒稳在 0.04 MB/s，而同样的链路单独拉别的站点并不慢——
典型的「按连接限速」。这种瓶颈靠换 DNS、换时段都没用，**多开几条连接就绕过去了**。

## 现在怎么下的

把文件切成几段，几条连接同时拉，各写各的位置（不需要事后拼接）：

- **最大 8 条连接**，按体积自动决定（约 12 MB 一段；小文件仍然单连接，
  因为建连本身要花钱）
- 每条连接只负责自己那一段，**断了只补那一段**（HTTP Range 续传），
  不必整包重下。在这条 40 KB/s 的链路上，这一点是决定性的
- 服务端要是不支持分段（老 release、中间代理把 Range 头剥掉了），
  **自动安静地退回单连接**——宁可慢，不能下不到
- 校验只增不减：体积、PE 头照旧，另外**新增官方 SHA-256 比对**
  （GitHub 在发行版里给了摘要就逐字节核对，没给就跳过）

进度显示也改了：除了百分比，现在会显示**当前速度和「剩余约 X 分钟」**。
以前那个速度下只报百分比，看起来就像卡死了。

实测结果（就是本版这个安装包本身，107 MB，走本机网络）：

```
8 条连接   平均 0.28 MB/s   6 分 07 秒    ← 本版（107 MB 切成 8 段并行）
单条连接   0.04 MB/s        约 43 分钟    ← 上一版
```

**慢的网络上收益最大；网速本来就快的话几乎没差别**（快链路单连接就能吃满带宽，
此时分段不会更快，只会多几条连接）。

## 网络不好时的额外收益

断流以前意味着「从 0 开始重下」。现在只补断掉的那一段，而且是自动的：
每一段最多重试 3 次，每次接着上次的字节往下拉。

## 顺带修的一件事：更新说明不会再是空的

之前几个版本的 Release 页面点开只有一行 "Full Changelog" 链接，看不到
「这版改了什么」——因为发布流程只让 GitHub 自动生成变更列表。现在更新说明
写在仓库里（`docs/releases/<版本号>.md`），发版时自动作为正文；这次开始生效，
v2.3.8 与 v2.3.9 的说明也补上了。

## 升级方式

用「检查更新」直接升级即可。这一版**建议所有人在旧版本上手动装一次**——
旧版本的下载走的是单连接，装完之后后续更新才享受多连接。
