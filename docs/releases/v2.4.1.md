# v2.4.1 — 数据操作搬到后台、页面白屏能自愈、内存有了账本

这一版处理三件用户报上来的事，都属于「用久了会碰到」的类型，不是新功能。

## 1. 迁移数据 / 清空全部 / 清缓存 / 启用私有安装：不再假死

这四个动作以前直接在界面线程里跑 `copytree` / `rmtree`。数据根 727 MB、
6.6 万个文件，实际耗时十几秒到几十秒——期间窗口不重绘，Windows 还会盖一层
「未响应」白纱，用户以为程序死了，其实它只是在数盘。

现在：

- 复制与删除都在**后台线程**里做，界面全程可响应，不再出现「未响应」
- 弹一个**带真实进度条**的窗口：`12345 / 66447 个文件（18%）`，
  下面一行是正在处理的文件名
- 迁移时**连"删旧目录"也在后台**——否则"迁移完成"之后还要再卡十几秒
- 进度回调**节流到每 80 ms 一次**。6.6 万个文件逐个发跨线程信号，
  等于把 6.6 万个事件灌进界面线程，那和没搬走是一样的病
- 任务进行中**不允许关窗**：复制到一半被关掉会留下"半个新目录"，
  那是最难收拾的状态

顺带修掉一个测试中才暴露的坑：进度文案原本边跑边写 `host.log`，而
"清缓存"正要删掉 `logs` 目录——一边删目录一边往里 open 新文件，Windows 上
会撞"文件被占用"；迁移时日志路径还会中途换成新根，那几行会直接落空。
现在进展先攒着，收尾时一次性写入。

实测：2000 个文件清缓存 5.0 s、600 个文件迁移 3.4 s（含旧目录清理与指针切换），
期间界面事件循环持续运转。

## 2. 页面长时间跑任务后变空白：现在会自己恢复

症状是「AI 跑着跑着页面白了，只能关掉重开」。根因是渲染进程没了或卡死时，
QtWebEngine **不会自己恢复**——它不弹崩溃页，就是一片空白，而主窗口此前
没有任何监听。

现在两条路径都盯住了：

| 情况 | 怎么发现 | 怎么处理 |
|---|---|---|
| 渲染进程退出（崩溃 / 被系统杀掉） | `renderProcessTerminated` 信号 | 记下退出码与当时的整棵树内存，0.5 s 后自动重载 |
| 进程活着但页面空了 | 每 15 s 一次 JS 心跳（`document.body` 子元素数） | 连续 3 次为空（约 45 s）自动重载 |
| 进程活着但主循环卡死 | 同一次心跳超时 25 s 未返回 | 自动重载 |

防循环：120 秒内最多自动恢复 3 次，超了就停手并提示用户手动刷新——
避免"恢复→崩→恢复"的死循环把 CPU 吃满。自动恢复时会发一条托盘气泡，
说明"刚才刷新了一下"是什么原因，不然用户只会觉得莫名其妙。

另外恢复动作统一走 `_recover_page()`：只有当前是 http/https 才 `reload()`，
否则退回带令牌的入口地址。**这条是照旧坑**——`reload()` 会把 `about:blank`
再载一遍，用户看到的就是"刷新了还是白的"。

## 3. 内存：先把账记清楚，再谈是不是泄露

「WebEngine 占了 1.7 GB」这个数字本身不足以判断。现场勘验（同一时刻）：

| 进程 | 常驻(WS) | 已提交(Private) |
|---|---|---|
| 网页渲染进程 | 16 ~ 1281 MB（随系统裁剪来回变） | **1307 MB** |
| node（DSH 服务） | 300 MB | 435 MB |
| 桌面壳（Python+Qt） | 298 MB | 525 MB |

两个关键事实：

- **常驻内存会被系统随时裁剪**。窗口最小化后，渲染进程的 WS 从 1281 MB
  掉到 16 MB，看着像"释放了"，但 Private 一点没动。所以拿任务管理器里
  那个数字判断"占了多少"会严重高估。
- **空转 6 分钟，渲染进程 Private 只涨 0.1 MB**。没有"持续增长"的证据，
  现阶段不能叫泄露；更像 **高水位不归还**——曾冲到 1.3 GB，
  之后 Chromium 没有把空闲页还给系统（WS 只剩一百多 MB 就是证据）。

最可能的来源是那次会话本身很重：该会话 3926 条记录、约 9.9 MB 文本
（4 小时、600 多次工具调用），前端把整段对话的 DOM 与高亮都留在页面里。
这属于上游前端的实现，桌面壳改不了。

所以这一版加的是**账本**，不是"修泄露"：

- 每分钟在 `logs/mem.log` 记一行：壳 / 网页 / node 三部分的 WS 与 Private，
  外加页面里的 JS 堆占用与 DOM 节点数
- 网页进程超过 1200 MB 时，日志里附一句"可「重新加载页面」释放"
- 渲染进程退出时，把当时的整棵树内存一起写进日志——这是区分
  「自己崩」和「被系统杀掉（内存不足）」的唯一现场证据

下一次再看到占用异常，看 `mem.log` 就能回答：是持续上涨（真泄露），
还是冲到高点后不回落（高水位），以及是 JS 活对象多还是 DOM 节点多。

## 4. 点「下载 session」没反应：下载被静默取消了

这一条是老大试用时发现的：界面上的下载按钮点下去毫无反应，没有文件、没有报错、
也没有提示。

原因不在页面，在桌面壳：DSH 的导出按钮是
`document.createElement("a")` 加 `download` 属性再 `click()`。在浏览器里这会进
下载管理器；而在 QtWebEngine 里，**没人接 `QWebEngineProfile.downloadRequested`
时请求被直接取消**，而且不报错不提示。更麻烦的是 `a.click()` 是同步返回的，
前端以为"已经交给浏览器了"，所以界面上什么都不会变。

同一类问题的第三个（前两个是"点复制没反应"和 `window.open` 得到空白窗口），
共同点是：**Qt 的默认行为是拒绝，而且拒绝得一声不响。**

现在：

- 点下载会弹**保存对话框**（默认落在系统"下载"文件夹，文件名由 DSH 给）
- 接受后开始 / 完成 / 中断各发一条托盘气泡，`host.log` 也留一行
- 文件名过一遍清洗（网页给的名字不可信），同名文件加 `(1)` 而不是静默覆盖
- 用户在对话框里取消 = 显式 `cancel()`，不让请求悬着

顺手核实了前端用到的其它浏览器能力：`showSaveFilePicker`、`requestFullscreen`、
`getUserMedia`、`window.print` **都没有用到**，所以暂时没有同类的隐性失效。
权限处理器现在把每次拒绝都写进 `host.log`——这类"没反应"事后只能靠日志查。

## 5. 点开插件配置的下拉框后，页面"只剩下拉框"（本轮修复）

现场：在插件配置弹窗里点开一个 `<select>` 下拉框，页面像"刷新"了一样，
只剩展开的下拉框内容，其余部分全消失；关掉下拉框也不恢复，点"重新加载页面"
也没用，只有把窗口关到托盘再打开才恢复。

查下来**根本不是切页**：Web 视图**停止呈现**了（DOM/JS 完全正常、渲染进程也没崩），
把启动时垫在下面的加载页露了出来——所以看起来像"回到了加载页"。

触发条件（探针实测）：加载页在 `StackAll` 里一直可见、且它的不确定进度条在**一直动画**
时，打开 `<select>` 原生弹层就有约 8~9/10 的概率让主视图停帧；`reload` 无效，
`view.update()` 一次即可恢复，每次弹层都要补。

修复三层：

- **停掉加载页动画**：视图露出后把进度条从"不确定"改成静止（顺带省掉一个常驻定时器）；
  再需要显示加载页时自动恢复动画。
- **弹层补帧**：应用级监听所有 `Qt::Popup` 顶层窗口的出现/关闭，在 0/60/260 ms
  给主视图 `update()`。每个弹层都补，不是一次性。
- **兜底重建视图**：自动恢复次数用尽时重建整个 Web 视图（保留登录态，有限流）；
  手动「重新加载页面」连按第二次也会直接重建。

顺带修掉一个此前"看起来有、其实没跑过"的功能：自动恢复原先调用了
`QWebEnginePage.reload()`，而 PySide6 6.11 根本没有这个方法，异常被 Qt 吞掉了。

## 6. 选中文本闪退：默认硬件加速 + 崩溃后自动降级

两次闪退的崩溃转储**逐帧相同**：都发生在 QtWebEngine 的 GPU 线程
（`Chrome_InProcGpuThread`），位置 `Qt6WebEngineCore+0xd224d3`，
是 ANGLE 缓存里的空指针读取。Qt 上游暂无修复，6.12.0 的同一段机器码逐字节相同，
所以**升级 Qt 不解决**。

这一版没有直接默认关掉硬件加速（那会让所有人都付性能代价，实测动画帧率
59.6 → 26.6 fps），而是：

- **默认仍走硬件加速**（QtWebEngine 的正常默认）；
- 启动时写一个"运行中"标记，正常退出时删除。**下一次启动若发现上次没正常退出**
  （原生崩溃/被杀），本次自动改用软件渲染，并在托盘提示一句；本次正常退出后，
  **再下次自动恢复硬件加速**；
- 控制面板「常规」页新增「硬件加速渲染」开关（重启生效）；
  也可在 `settings.json` 里把 `webengine_hw_accel` 设为 `false` 强制软件渲染；
- 启动日志会记录本次实际使用的渲染参数与（若降级的）原因，方便排查。
