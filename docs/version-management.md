# 版本管理设计

> 2026-11-16 写。回答一个问题：**启动器该怎样管 DSH 的版本**，
> 以及这套东西和现有的"更新/回退"怎么共存。

---

## 一、现在的样子（问题）

私有安装是**一份**，路径固定：

```
%LOCALAPPDATA%\DSH-Web\node-global\node_modules\@deepseek-ai\dsh\
```

"更新"和"回退"都是对**这一份**做覆盖式安装：

| 动作 | 现在的实现 | 代价 |
|---|---|---|
| 更新 | `npm i -g @deepseek-ai/dsh@<新版本>`（先卸载旧的） | 6 分钟、656 个包 |
| 回退 | 装回 `last_good_version` | 同样要重新下载 |

**三个真问题**：

1. **回退不是回退，是重装。** 用户点"回滚"要再等几分钟，而且如果那个版本
   在 npm 上被 unpublish（预发布包尤其常见），就再也回不去了。
2. **只能往回退一步。** `last_good_version` 只记一个值，退两步没有信息。
3. **没法"不升"。** 用户知道新版本会打断插件，但他能做的只是"永远不点更新"。
   一旦点了，旧版本当场消失。

老大提的正是第 3 点：新用户不一定会用最新版，因为插件生态还没适配。
**这恰恰是启动器应该解决的问题**——启动器可以持有多个版本，让切换变成一次指针移动。

---

## 二、目标

```
用户视角：
  · 我能看到这台机器上有哪几个 DSH 版本
  · 我可以随时切到任何一个已安装的版本（秒级，不下载）
  · 我可以装一个新版本，但旧的不消失
  · 我知道哪个版本跟我的插件配合得好
```

一句话：**版本库 + 指针**，而不是**一份安装 + 反复覆盖**。

---

## 三、方案：版本库

### 3.1 目录结构

```
%LOCALAPPDATA%\DSH-Web\versions\
  0.2.2-rc.1\                 ← 每个版本一个完整 npm prefix
    node_modules\@deepseek-ai\dsh\...
    node\                     （如果将来需要独立 node）
  0.2.2-rc.3\
  index.json                  ← 版本清单 + 元数据 + 当前指向
```

`index.json` 大致长这样：

```json
{
  "active": "0.2.2-rc.1",
  "versions": [
    {"version": "0.2.2-rc.1", "installed_at": "2026-11-16T21:00:00",
     "size_mb": 254, "last_used": "...", "health": "ok", "note": ""},
    {"version": "0.2.2-rc.3", "installed_at": "...",
     "size_mb": 261, "last_used": "...", "health": "plugin_broken",
     "note": "dsh-cost-meter 加载失败"}
  ]
}
```

### 3.2 切换怎么做（关键实现约束）

**不用软链。** Windows 上创建符号链接要么需要管理员权限、要么需要开发者模式，
这两条都不能指望用户满足。而且软链会让"这个目录到底是哪一份"变得难以排查。

正确做法是**让 `DshInstall.prefix` 指向选中的版本目录**：

```python
prefix = os.path.join(config.versions_dir(), active_version)
install = contract.resolve(prefix=prefix)      # 已有的解析入口
```

`DshInstall` 本来就带 `prefix` 字段，`npm install -g --prefix <dir>` 也一直是
按 prefix 走的——**版本库不需要改动安装机制本身**，只需要改"指向哪个 prefix"。

切换的完整动作：

1. 停服务（node_modules 在 Windows 上会被占用）
2. 改 `index.json` 的 `active`
3. 重新 `resolve` 出 install
4. 起服务（约 10~15 秒）

**注意**：这仍然是"重启服务"，不是"热切换"。DSH 没有热重载安装的能力，
所以切换的时间成本 ≈ 一次正常启动。但比"重新下载 6 分钟"好得多。

### 3.3 安装新版本

```python
npm install -g --prefix versions/<ver> @deepseek-ai/dsh@<ver>
```

与现有 `install_version()` 的区别只有 `--prefix` 指向版本目录，**其余完全复用**
（包括 `fresh=True` 的卸载逻辑、`remove_drifted()` 的半升级治理、`verify()`）。

这一点很重要：**版本库不应该重写安装流程**，它只是把"装到哪"参数化。
现有那些踩过坑的修复（子依赖漂移、卸载残留）必须原样继承。

### 3.4 磁盘

实测一份 DSH 约 250 MB（656 个包）。策略：

- **默认保留 2 个版本**（当前 + 上一个）。够用了——回退一步是最高频的场景。
- 每个版本旁显示体积，删除前明确告知会释放多少。
- 超过 3 个时在版本页顶部提示"占用了 xxx MB"，但不自动删。
- **不要默认保留全部**。有人守着 6 个预发布版本，一年多花 1.5 GB，
  而且他根本不知道自己有这些。

## 四、和现有更新的关系（这块最需要说清楚）

现在的"更新"是**动作**：查最新版 → 装 → 覆盖。
加入版本库之后，它应该拆成两件事：

| | 以前 | 以后 |
|---|---|---|
| **检查更新** | 查完直接问"要不要装" | 只查、只显示"有新版"（不装） |
| **安装** | 覆盖当前那份 | 在版本库里新增一份，**旧的不动** |
| **切换** | 不存在 | 改指针（秒级） |
| **回退** | 重新下载旧版 | 切回已安装的旧版（**不下载**） |

于是**更新变成"新增 + 切换"**，而回退变成"切回去"。

三个直接结果：

1. `last_good_version` / `previous_version` 这套状态可以**退役**——
   版本库天然记得所有版本，"哪个是好的"由 `active` 和 `health` 表达。
   保留它们只会出现两个真相来源（哪份说了算？）。
2. "自动回滚"要重新定义：以前是"装回上一版"，现在是"切回上一版"。
   逻辑更简单，也不会再因为下载失败而回滚失败。
3. **更新失败不再有破坏性**：新版本装在独立目录，装坏了只是多一个坏目录，
   删掉即可。当前在用的那份从头到尾没被碰过。

> 这条是版本管理最大的收益，比"能选版本"本身更重要：
> **它把"更新"从一次有风险的覆盖，变成一次可撤销的增量。**

## 五、公共安装（系统那份 DSH）怎么办

这是必须划清的边界。公共安装住在系统 npm 全局目录里（`/usr/lib/node_modules`
或用户级 prefix），**我们能读、能装、但不能版本化**——那个目录归 npm 和
用户的其他命令行操作管，我们不该在里面维护多份副本。

所以规则是：

| 来源 | 版本库支持 |
|---|---|
| **私有安装** | 完整支持：多版本、切换、删除 |
| **公共安装** | 只支持"锁定版本"：不允许我们动它，只提示当前版本 |
| **公共 → 私有** | 提供"导入为私有副本"，之后就能版本化了（已有 `import_private`） |

界面上要明确区分，不能让用户以为公共安装也能切版本。
公共安装那一行给一句解释："这份由系统 npm 管理，版本库只能管私有安装。
点『复制为私有副本』之后就能自由切换了。"

## 六、插件兼容性：能自动评估，但要如实表达不确定性

老大提醒了一件我原先不知道的事：**官方要求插件在 package.json 里声明适配的
DSH 版本**。去实测确认了——字段是 `engines.dsh`，语义是 npm 版本范围。

### 6.1 实测到的普及率

扫了本机 `profiles/web/node_modules` 下 149 个包，其中 **18 个是 DSH 插件**
（有 `dsh` 元数据），**只有 6 个声明了 `engines.dsh`**：

| 插件 | 声明 |
|---|---|
| `dsh-comfyui` | `>=0.1.2-alpha.4 <0.3.0-0` |
| `dsh-context` | `>=0.2.0-rc.2 \|\| >=0.2.1-rc.2 \|\| >=0.2.2-rc.1` |
| `dsh-cost-meter` | `>=0.2.0-rc.1 <0.3.0-0` |
| `dsh-mnemon` | `>=0.2.0-rc.2 <0.2.1-0 \|\| >=0.2.1-rc.1 <0.3.0-0` |
| `dsh-ops` | `>=0.2.2-rc.1 <0.2.3-0` |

其余 12 个（多为 mnemon 的 source-*/strategy-* 子包）只有 `dsh` 元数据、没声明范围。

**三分之一的覆盖率**，但恰好覆盖了最活跃的那几个。所以这条路值得做，
但不能宣称"兼容性已检查完毕"。

### 6.2 三态，不是二态

| 状态 | 判据 | 界面表达 |
|---|---|---|
| **适配** | 有 `engines.dsh` 且目标版本满足 | 绿点 · 声明支持 |
| **不明确** | 没有 `engines.dsh` | 灰点 · 未声明（**不是"兼容"**） |
| **不匹配** | 有声明但目标版本不满足 | 黄点 · 声明只支持 x~y |

**"未声明"绝不能显示成绿点。** 那是把"作者没说"当成"作者说可以"，
用户会据此做出错误决定。这条边界必须守住。

### 6.3 怎么算

不要自己实现 semver——预发布版本的比较规则（`0.2.2-rc.1 < 0.2.2`、`rc.2 > rc.1`）
和 `||` 组合很容易写错，而写错的后果是给出**看起来权威的错误结论**。

实测可行的做法：用 DSH 自己依赖树里的 `semver`（`profiles/web/node_modules/semver`
一直在），一次批量求值：

```javascript
// 传 [{version, range}, ...]，返回 [true, false, ...]
const semver = require('semver');
list.map(x => semver.satisfies(x.version, x.range, { includePrerelease: true }));
```

实测三种真实写法都判断正确：

```
0.2.2-rc.1 vs >=0.2.0-rc.1 <0.3.0-0                          → true
0.2.2-rc.1 vs >=0.2.0-rc.2 <0.2.1-0 || >=0.2.1-rc.1 <0.3.0-0 → true
0.1.5      vs >=0.2.0-rc.1 <0.3.0-0                          → false
```

**降级路径**：拿不到 semver（DSH 版本太老、依赖被裁剪）时一律报"未声明"，
不要自己瞎猜。宁可少说，不要说错。

### 6.4 声明质量参差，所以结果要标出处

`dsh-context` 写的是 `>=0.2.0-rc.2 || >=0.2.1-rc.2 || >=0.2.2-rc.1`——
三个 OR 项其实第一个就涵盖了后两个，是作者抄模板留下的冗余。

所以评估结果旁边要注明依据：**"按插件声明的 engines.dsh 判断"**。
这是个**参考**，不是保证——作者可能写错、可能没来得及更新声明。
用户拿它做取舍依据，但不能拿着它去投诉"你说兼容的怎么崩了"。

### 6.5 和手动标记的关系

自动评估只解决"作者声明了"的那三分之一。剩下两种情况仍需要人：

- 声明了"未声明"的插件，用户用下来是好的 → 可以标记「我这套用着没问题」
- 声明支持但实际崩了 → 标记「声明说支持，实际不兼容」

所以界面上两套并存：

```
dsh-cost-meter 1.9.64        绿  声明支持 >=0.2.0-rc.1 <0.3.0-0
dsh-whale-widget 0.4.2       灰  未声明适配版本          [我标记为可用]
dsh-ops 0.5.4                黄  声明只支持 >=0.2.2-rc.1 <0.2.3-0
```

**手动标记优先于自动结论**（用户的实际体验比作者的声明更可信），
并在界面上区分来源：`[自动]` vs `[你标记的]`。

## 七、界面（新 Tab「版本」）

放在「运行方式」之后，叫「版本」。

```
┌─ 当前 ────────────────────────────────┐
│ 0.2.2-rc.1 · 私有安装 · 254 MB          │
│ [检查新版本]                            │
└───────────────────────────────────────┘

┌─ 已安装 ──────────────────────────────┐
│ ● 0.2.2-rc.1   11-16 安装   254 MB     │
│   当前使用                              │
│   插件：1 个不匹配 · 3 个未声明  [详情]  │
│ ○ 0.2.2-rc.3   11-14 安装   261 MB  ⚠  │
│   dsh-cost-meter 声明只支持 <0.3.0     │
│   [切换] [删除]                         │
└───────────────────────────────────────┘

┌─ 可安装 ──────────────────────────────┐
│ 0.2.2-rc.3 (next)   2026-11-14        │
│ 0.2.1 (稳定)        2026-11-02  [安装] │
└───────────────────────────────────────┘
```

几条界面约束（**遵守 DSH 的 UI 规范，不用 Qt 原生控件自带的观感**）：

- 版本列表用现有的 `Card` + 行控件拼，不引入 `QListView`
- 任何下拉（选版本、选通道）都用项目里已有的 `QComboBox` + `style_combo` 路径，
  **不要指望系统默认样式**——记忆里踩过：popup 是独立顶层窗口，不吃父窗口 QSS，
  Win11 下会整块变黑
- 状态标记用现有 `StatusDot` 的语义色（ok / warn / bad），不要自造颜色

## 八、分期

| 阶段 | 内容 | 风险 |
|---|---|---|
| **P1** | 版本库目录 + `index.json` + "装到指定 prefix" + 切换（命令行可验） | 低，不动 UI |
| **P2** | 「版本」Tab：列表、切换、删除 | 中，新页面 |
| **P3** | 把"更新"改成"装新版本 + 切换"，退役 `last_good_version` | **中高，动核心流程** |
| **P4** | 公共安装的"复制为私有副本"入口；插件兼容性评估（读 `engines.dsh`）+ 手动标记 | 低 |

**P3 是分界线**：在它之前，版本库只是"多出来的一个功能"；在它之后，
更新流程才真正变成无损的。

> **2026-11-20 已完成**。两条路径都接上了：
> · `UpdateWorker` 在版本库启用时走"装到 versions/<目标> + 切指针"，
>   装失败只是多一个不完整目录，**当前那份从头到尾没被碰过**；
> · `_rollback` 先看版本库里有没有那个版本，有就直接切。
> 实测回滚 **34 秒**（其中约 20 秒是服务启动），老路径是 397 秒下载 + 启动。
> 版本库未启用时仍走原来的覆盖式安装，行为不变（渐进接入）。

## 九、还没想清楚的地方

诚实列出：

1. **DSH_HOME 共享**。所有版本共用同一个 `DSH_HOME`（会话、插件、凭据都在里面）。
   如果某个版本改了会话记录格式，切回旧版可能读不了——README 的"已知限制"
   里已经写了"回滚不保证数据格式可逆"，版本库**没有解决这个问题**，只是让它
   更容易发生（因为切换变便宜了）。
   缓解：切换前提示"数据目录会在新版本下被写入，回退后可能读不了"。
2. **版本库本身被谁升级**。`@deepseek-ai/dsh` 的 npm 缓存（`~/.npm/_cacache`）
   会慢慢变大，我们管不了它。
3. **预发布版本的生命周期**。rc 版本随时可能被 unpublish，所以"已安装"比
   "可安装"可靠——这也是版本库的价值之一，但不解决"想装一个已被删的版本"。
